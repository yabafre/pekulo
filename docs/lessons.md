### 2026-05-07 — `bun test` ≠ `vitest run` ; CI workflow must invoke per-package `test` script (Scope: aped-dev, aped-review — every CI workflow that runs vitest tests in this monorepo)

- **Date:** 2026-05-07
- **Mistake:** `.github/workflows/pr.yml#test-unit` step ran `bun test` whenever a `vitest.config.*` was found. `bun test` is Bun's native test runner — it does NOT execute vitest tests (`toMatchInlineSnapshot`, `vitest-axe`, `setupFiles`, `--testNamePattern` are vitest-specific). Result on CI: 150 / 212 tests failed because Bun tried to interpret vitest assertions and couldn't load the `setup.tsx` file. Locally `bun run test` works because the package's `test` script is `vitest run`.
- **Correction:** Switched the workflow step to `bun --filter='*' run test`, which routes to each workspace's own `test` script — vitest is invoked correctly on `@pekulo/ui`, `bun test` (or whatever the package configured) is invoked on `apps/api`.
- **Rule:** When wiring CI for a polyglot test setup (vitest + bun test + pytest, etc.), NEVER short-circuit to a specific runner at the workflow level. Always invoke the per-package `test` script via `bun --filter='*' run test` (or `pnpm --filter='*' test` / `yarn workspaces foreach run test`). The runner choice is a workspace concern; the workflow's job is to fan out. Apply when adding any new CI test step.
- **Architecture rationale (architecture L241):** the project deliberately runs vitest on `@pekulo/ui` + `apps/web` (DOM + React + axe-core ecosystem dep on `vitest-axe`) and bun test on `apps/api` (pure Node + Bun-native ergonomics). The split is intentional, not an oversight — apps/api's tests run ~5–10× faster on bun test than they would on vitest, but `@pekulo/ui` cannot drop vitest without losing the a11y harness. Future CI steps must respect both runners by going through per-package scripts.

### 2026-05-07 — `package.json#exports` cannot reference `./node_modules/<dep>/<file>` ; vendor the asset instead (Scope: aped-dev, aped-arch — every workspace package that re-exports a static asset from a transitive dep)

- **Date:** 2026-05-07
- **Mistake:** `packages/ui/package.json` declared `"./reset.css": "./node_modules/@tamagui/core/reset.css"` to expose `@tamagui/core`'s reset stylesheet via `@pekulo/ui/reset.css`. The path is relative to `packages/ui/`'s own `node_modules/`. Bun keeps `@tamagui/core` inside `packages/ui/node_modules/` (no aggressive hoisting), so locally `apps/web/src/app/layout.tsx`'s `import "@pekulo/ui/reset.css"` resolves. On Vercel (Yarn 4.5 install), `@tamagui/core` hoists to the **root** `node_modules/`, leaving the path `./node_modules/@tamagui/core/reset.css` unresolved. Build crashes with `Module not found: Can't resolve '@pekulo/ui/reset.css'`.
- **Correction:** Vendored the file at `packages/ui/public/reset.css` (631 bytes, copied verbatim from `@tamagui/core/reset.css`). Updated `exports`: `"./reset.css": "./public/reset.css"`. The vendored copy is owned by `@pekulo/ui` and survives any installer's hoisting strategy.
- **Rule:** A package's `exports` map MUST point only to files under the package's own tree (`src/`, `public/`, `dist/`, etc.). NEVER reference paths inside `./node_modules/` — those are install-strategy-dependent and break across installers. If a transitive dep ships a static asset (CSS, images, fonts) you want to re-expose, vendor a copy at build time (or at hand) and document the source. Generalises beyond Tamagui — apply when re-exposing any third-party asset (e.g. `@radix-ui` reset CSS, `@tamagui/font-inter` font files, etc.). Pre-1.0 packages in particular shuffle their asset paths between releases; vendoring also pins the version.

### 2026-05-07 — Re-exporting `tamagui` (or any module that calls `createContext` at load time) from a barrel without `"use client"` crashes Next.js RSC build (Scope: aped-dev, aped-arch — every `@pekulo/ui`-style barrel that re-exports React / DOM-bound modules)

- **Date:** 2026-05-07
- **Mistake:** Added `export { Text, View, styled } from "tamagui"` to the top of `packages/ui/src/index.ts` (the barrel) so apps could `import { Text } from "@pekulo/ui"` without declaring a direct `tamagui` dep. The barrel itself has no `"use client"` directive (it carries tokens / themes / Pekulo\* components — RSC-safe). Tamagui's module evaluation calls `createContext` at load time. Next.js's RSC server-pass evaluates the barrel for any consumer importing from `@pekulo/ui`, including `"use client"` pages — when it hits `import "tamagui"`, `createContext` fires server-side and crashes the prerender with `(0, ak.createContext) is not a function`. This is L17's mechanism (Tamagui in pure RSC) re-introduced via a barrel re-export.
- **Correction:** Moved Tamagui re-exports into a separate sub-module `packages/ui/src/client.ts` carrying its own `"use client"` directive. Exposed via the `@pekulo/ui/client` package sub-path (`exports` map). Consumers split their imports — `Section`, `useToast`, tokens, and Pekulo\* components from `@pekulo/ui` (RSC-safe); raw `Text` / `View` / `styled` from `@pekulo/ui/client` (client-only).
- **Rule:** A barrel that re-exports a module which performs side effects at module-load (`createContext`, global registrations, polyfills) MUST live behind a `"use client"` boundary OR be exposed via a separate sub-path with its own client directive. Never put `export * from "<dom-bound-package>"` at the top of an RSC-shared barrel. Generalises beyond Tamagui — apply to any future re-export of `react-aria`, `@radix-ui/react-*`, `framer-motion`, or any package that touches React's context API at module-evaluation time. Verify by importing from the barrel inside a Server Component during a Next build smoke; if the build prerender fails with `createContext is not a function` (or similar), the boundary is wrong.

### 2026-05-07 — Vercel's Yarn 4.5 hoisting trips Next.js's build-time TS check on `transpilePackages` deps' transitive `.ts` sources (Scope: aped-dev, aped-arch — every Next.js app on this monorepo deployed to Vercel that uses `transpilePackages`)

- **Date:** 2026-05-07
- **Mistake:** `apps/web/next.config.ts` declared `transpilePackages: ["@tamagui/next-theme", "react-native-web"]`. Locally Bun keeps `@tamagui/element` (transitive dep of `@tamagui/next-theme`) inside `packages/ui/node_modules/`, hidden from Next's TS check (which respects `apps/web/tsconfig.json#exclude: ["node_modules"]`). On Vercel, Yarn 4.5 hoists `@tamagui/element` to the **root** `node_modules/`. Next's build-time TS pass walks `transpilePackages` deps' transitive sources — `node_modules/@tamagui/element/src/types.ts:1:27` declares `import type { View } from 'react-native'`. `apps/web` aliases `react-native` → `react-native-web` at _runtime_ via `turbopack.resolveAlias` but does NOT declare `@types/react-native` for type resolution → `Cannot find module 'react-native'`.
- **Correction:** `typescript: { ignoreBuildErrors: true }` in `apps/web/next.config.ts`. The CI `typecheck` job (turbo `tsc --noEmit` per workspace) is the source-of-truth gate for type errors; it respects `tsconfig.json#exclude` and runs against the workspace's own files only. Adding `@types/react-native` to `apps/web` would be heavier (250+ KB of RN types in the resolution scope) and unnecessary when the CI gate already covers us.
- **Rule:** When `transpilePackages` is set on a Next.js app deployed to Vercel (or any installer that aggressively hoists transitive deps to root), set `typescript: { ignoreBuildErrors: true }` and rely on a separate CI typecheck job. Next.js's build-time TS pass does NOT match what `tsc --noEmit` does at the workspace level — it widens its scope to walk transpiled packages' source. Apply to every future Next.js app added under `apps/*` that uses `transpilePackages`. If you genuinely want Next's TS check to be the gate, declare `@types/<every-rn-touching-dep>` explicitly — but the CI-job-as-gate path is simpler and matches the repo's existing turbo-driven pattern.

### 2026-05-07 — Domain types live in `@pekulo/types` ; `@pekulo/ui` is for component code only (Scope: aped-dev, aped-arch, aped-review — every `@pekulo/*` package in this monorepo, every UI / API / mobile workspace consuming domain entities)

- **Date:** 2026-05-07
- **Mistake:** Story 0-10 inlined 8 domain entities + their literal-union enums directly in `@pekulo/ui` component files (`PekuloAccountRow.tsx` defined `PekuloAccountType`, `PekuloMilestoneRow.tsx` defined `PekuloMilestone` + `MilestoneStatus`, etc.). Architecture L366 says "Domain TS types (in @pekulo/types or apps): PascalCase (Account, Holding, MonthlyRecord, ...)" — no `Pekulo` prefix on TYPES (the prefix is for COMPONENTS). Story 0-10 violated both rules: prefixed names AND wrong package. The user surfaced this mid-review with "pourquoi tout est en dure dans les components, et non dans les types et autres ?".
- **Correction:** Extracted `Account`, `Holding`, `Activity`, `Suggestion`, `Milestone`, `MonthlyRecord`, `Property`, `CompositionItem` + their literal-union enums (`AccountType`, `HoldingKind`, `TxDirection`, `LlmRoute`, `MilestoneStatus`, `StatTone`) into `packages/types/src/index.ts`. Added const arrays (`ACCOUNT_TYPES`, `HOLDING_KINDS`, `TX_DIRECTIONS`, `LLM_ROUTES`, `MILESTONE_STATUSES`, `STAT_TONES`) per architecture L368. `@pekulo/ui` declared `@pekulo/types` as a workspace dep and now imports from it; component prop types stay co-located but reference `Account`, `Holding`, etc. instead of inlining. Components keep their `Pekulo*` prefix; types lose the prefix.
- **Rule:** Every domain entity (anything that describes a row of business data — Account, Holding, Transaction, Milestone, Property, etc.) MUST live in `@pekulo/types`. Component PROP interfaces (`Pekulo<Component>Props`) can stay co-located in `@pekulo/ui` because they're component-API concerns, but they MUST reference the domain type from `@pekulo/types`, not redefine it. When adding any new domain in feature epics 1–9: (a) define the entity + literal-union enum + const array in `@pekulo/types/src/index.ts` first, (b) import into `@pekulo/ui` for the component, (c) import into `@pekulo/contracts` for the oRPC contract, (d) import into `apps/web/src/lib/services/` for the service layer. Generalises beyond UI — apps/api Prisma DTOs should also derive from `@pekulo/types` shapes where the wire contract matches the domain.

### 2026-05-07 — `pekuloColors` is a 1:1 mirror of the SSOT, never a fork ; extensions land in the SSOT first (Scope: aped-dev, aped-arch, aped-review — every token added to `@pekulo/ui`'s palette in this monorepo)

- **Date:** 2026-05-07
- **Mistake:** Story 0-10's `packages/ui/src/tokens/colors.ts` was a **structural fork** of the SSOT (`docs/ux-preview/src/tokens/colors.ts`). It exposed `accent.500/400` + `semantic.{success,warning,danger,info}` instead of the SSOT's `perf.{gain,gainSoft,loss,lossSoft,neutral}` + `dataBlue` + `surface.overlay`. Missing entirely from the mirror: `perf.gainSoft`, `perf.lossSoft`, `perf.neutral`, `dataBlue`, `surface.overlay`. Worse, the mirror invented `#FBBF24` warning amber with no SSOT origin — used by `PekuloSuggestionRow` for LLM-confidence labels. Memory rule (`feedback_ssot_ux_preview`): "subset OK, fork no". Story violated both halves.
- **Correction:** Re-ported `packages/ui/src/tokens/colors.ts` 1:1 from the SSOT structure. Theme files (`pekulo-dark.ts`, `pekulo-light.ts`) keep ergonomic aliases (`$accent` → `perf.gain`, `$success` → `perf.gain`, `$danger` → `perf.loss`, `$info` → `dataBlue`) for component-code ergonomics, and add the SSOT-aligned keys (`$perfGain`, `$perfGainSoft`, `$perfLoss`, `$perfLossSoft`, `$perfNeutral`, `$dataBlue`, `$backgroundOverlay`). The amber `--warning` extension was added to the SSOT FIRST (`docs/ux-preview/src/index.css#:root` + `.light` + `@theme inline`) AND `docs/ux-preview/src/tokens/colors.ts`, with file-header documentation that it's a Pekulo extension (NOT a TR primitive — used only for LLM-confidence labels < 75 %).
- **Rule:** Before adding ANY new token (color, spacing, radius, font size, etc.) to `@pekulo/ui`, the workflow is: (1) add it to `docs/ux-preview/src/index.css` (the runtime SSOT) with a justifying comment, (2) mirror it 1:1 in `docs/ux-preview/src/tokens/colors.ts` (or the relevant token file), (3) re-mirror in `packages/ui/src/tokens/<file>.ts`. The Pekulo TS mirror is downstream — never invent values there. If a new token is a Pekulo-specific extension (not a TR primitive), document the divergence in the file header of all three layers. Apply when extending the palette / scale / typography in any future story (1-X compass UI, 5-X transactions UI confidence indicators, 7-X dashboard accent surfaces, etc.). The reviewer (`aped-review`'s Aria specialist) checks for fork divergence on every UI story.

### 2026-05-07 — TR-strict palette: `$accent` (emerald) is reserved STRICTLY for ± monetary deltas ; control chrome stays grayscale (Scope: aped-dev, aped-review — every Pekulo\* component touching state-color tokens)

- **Date:** 2026-05-07
- **Mistake:** Story 0-10 painted toggle/radio/slider control chrome with `$accent` (emerald `#00d26a`) — `PekuloToggleRow.tsx:29` `checked: { true: { backgroundColor: "$accent" } }`, `PekuloRadioGroup.tsx:28` `<TamaRadioGroup.Indicator backgroundColor="$accent" />`, `PekuloSlider.tsx:15` `<TamaSlider.TrackActive backgroundColor="$accent" />`. The Sparkles LLM-category icon in `PekuloSuggestionRow.tsx:66` also rendered emerald via `var(--accent)`. User memory `feedback_trade_republic_fidelity`: "emerald ONLY on perf deltas". A toggle ON state, radio indicator, slider active track, and LLM-category sparkle are all CHROME, not deltas. UX-preview reference (`apps/ux-preview/src/App.tsx:1894`) uses `bg-fg` (white) for the active toggle state.

Kept `$accent` legitimate on `PekuloHero.tsx#aheadEur` (perf delta) and `PekuloHypothesisVerdict#delta` (perf delta). Sparkles icon → `var(--colorSecondary)` (grayscale chrome). Toggle knob ON `$colorOnAccent` → `$background` (`#000` knob on white track, like iOS).

Control state (on/off, selected/unselected, active/inactive), focus rings, hover states, and decorative chrome (icons next to labels) stay on grayscale (`$color`, `$colorSecondary`, `$colorTertiary`, `$colorOnAccent`). The reviewer (`aped-review`'s Aria specialist) grep-walks `$accent` consumers and challenges every non-delta usage. Generalises to `$danger` (red) — tone for LOSS deltas, not for "destructive button" chrome (use `$colorTertiary` + a separate confirmation step).

### 2026-05-06 — Tamagui v2 prop renames vs v1: `tag` → `render`, `animation` → `transition` (Scope: aped-dev, aped-arch — every Tamagui v2-rc.41+ component file in this monorepo)

- **Date:** 2026-05-06
- **Mistake:** Story 0-10 transcribed Tamagui v1 prop syntax verbatim (`<View tag="section">`, `<TamaDialog.Content animation="quick">`, `styled(View, { tag: "button" })`). Tamagui v2-rc.41 renamed both: `tag` → `render` (on View/Text and inside `styled()` options) and `animation` → `transition`. Story T4.1, T4.4, T4bis.1–T4bis.9, T5.9–T5.12, T6.10–T6.12 all needed the rename to typecheck. The `TamaguiCustomConfig` augmentation also moved: in v2-rc.41 the interface lives in `@tamagui/web/types/types.d.ts`, NOT `@tamagui/core` (which v1 used) — the augmentation must target `declare module "@tamagui/web"` to propagate registered config types (notably `media` keys) to View/Text consumers imported from `tamagui`.
- **Correction:** Per Alex's directive ("on ne rétrograde rien, on fix avec ce qui est recommandé pour la v2"), every primitive + component was rewritten using the v2 syntax. context7 confirmed both renames against `https://tamagui.dev/docs/guides/how-to-upgrade` migration checklist. The augmentation target was diagnosed by adding a typed probe (`type Keys = keyof typeof config["media"]`) and tracing where `TamaguiCustomConfig` is declared in node_modules.
- **Rule:** When migrating any Tamagui v1 → v2-rc code or transcribing an LLM-authored story:
  1. Replace `tag="<el>"` (on View/Text/styled options) with `render="<el>"`.
  2. Replace `animation="<key>"` with `transition="<key>"`.
  3. `declare module "@tamagui/web" { interface TamaguiCustomConfig extends typeof config {} }` — NOT `@tamagui/core`.
  4. v2 default media keys are mobile-first Tailwind-aligned: `$sm/$md/$lg/$xl/$xxl` = min-width 640/768/1024/1280/1536. v1's `gtMd` (>1020) maps closest to v2's `$lg` (>1024). For "max-width" use the kebab-case `$max-md` form.

### 2026-05-06 — Tamagui v2 `Select.Content` is a FocusScope wrapper, not a styled View — style props go on `.Viewport` (Scope: aped-dev — every `@tamagui/select` consumer in this monorepo)

- **Date:** 2026-05-06
- **Mistake:** Story 0-10 T4bis.5 placed `zIndex={200000}` directly on `<TamaSelect.Content>`. v2-rc.41's Select.Content is a `FocusScope`-typed component (props: `loop?`, `trapped?`, `onMountAutoFocus?`, etc.) that does not accept Tamagui style props. The styled View inside Select is the `.Viewport` part.
- **Correction:** Moved `zIndex` onto `<TamaSelect.Viewport>`, kept Content props limited to scope/focus options.

### 2026-05-06 — `@tamagui/popover|tooltip|select` triggers must `render="button"` to satisfy axe-core's `aria-allowed-attr` (Scope: aped-dev, aped-qa — every Tamagui compound trigger surface in this monorepo)

- **Date:** 2026-05-06
- **Mistake:** Story 0-10 T4bis.3 wrapped `<TamaPopover.Trigger>` around a `<Text>` child and let Tamagui render its default `<div>` element. axe-core 4.x flags `aria-expanded` / `aria-haspopup` / `aria-controls` (auto-injected by the popover) as `critical` violations on a `<div>` — those ARIA attrs are only valid on focusable, button-semantic roles. The a11y test failed with `aria-allowed-attr: ARIA attribute is not allowed: aria-expanded="false"`.
- **Correction:** Wrapper triggers force `render="button" unstyled` so the auto-generated ARIA attrs land on a real `<button>`. Same fix applied to `<PekuloTooltip.Trigger>`. Select.Trigger already rendered as button by default.
- **Rule:** For any Tamagui compound primitive whose `.Trigger` injects `aria-*` attributes, the wrapper MUST force `render="button"` (or `render="a"` for link triggers). Verify via `bun --filter='@pekulo/ui' run test:axe` after each new wrapper lands.

### 2026-05-06 — Tamagui in pure Server Components crashes Next.js build with "createContext is not a function" — keep Tamagui under `"use client"` boundaries (Scope: aped-dev — every apps/web RSC route that touches @pekulo/ui or tamagui imports)

- **Date:** 2026-05-06
- **Mistake:** Story 0-10 T7.5/T7.6/T7.7 specified `<View>` and `<Text>` from tamagui inside `apps/web/src/app/dashboard/{layout,page,loading}.tsx` — all Server Components (no `"use client"`). The build's "Collecting page data" step crashed with `(0, i.createContext) is not a function. (In '(0, i.createContext)("")', '(0, i.createContext)' is undefined)` because Tamagui's module-evaluation calls `createContext` at server-module-load time, and Next.js's server bundle's React import shape doesn't expose it the same way as the client bundle.
- **Correction:** RSC routes use plain HTML chrome (`<div>` / `<header>` / `<main>` with inline `style={{ ... }}` referencing the theme CSS vars: `var(--color)`, `var(--background)`, etc.). Pekulo client primitives (Section, EmptyState, Skeleton) consumed inside the server tree work fine — they carry their own `"use client"` boundaries. The animation hooks `use-count-up.ts` and `use-stagger.ts` also gained `"use client"` directives at the top because they call `useState` / `useEffect` / `useSyncExternalStore` and were being pulled into the server graph via the `@pekulo/ui` barrel.
- **Rule:** RSC routes that need server data fetching (auth, supabase) should use plain HTML + CSS-var inline styles for chrome. Tamagui imports MUST live behind a `"use client"` boundary — either at the page level (`"use client"` directive) or inside a Pekulo\* primitive that already declares one. Animation hooks and any package module that imports from React's hooks API need `"use client"` too if they sit in a barrel that's imported by RSC.

### 2026-05-06 — Tamagui v2 `styled.input` / `styled.button` style options are restricted to StackStyle — text-style props (color/fontSize/outline) need inline `style={...}` (Scope: aped-dev — every Pekulo styled HTML input/button surface)

- **Date:** 2026-05-06
- **Mistake:** Story 0-10 T7.4 specified `<View tag="input" color="$color" fontSize={14} />` for the auth form's text inputs. v2-rc.41's `styled.input` and `styled.button` HTML factories restrict their style options to `Partial<StackStyle>` — `color`, `fontSize`, `outline*` are NOT in StackStyle (they're TextStyle props, only allowed on `TextLikeElements` like span/a/label). The typecheck failed with `'color' / 'fontSize' does not exist in type 'Partial<StackStyle>'`.
- **Correction:** `auth-form.tsx` uses `styled.input({...layout-only props...})` for the React-Native-style props (backgroundColor, borderRadius, paddingHorizontal/Vertical, borderWidth) and adds `style={{ color: "var(--color)", fontSize: 14, outline: "none" }}` inline on the JSX element for the text-style props referencing the theme CSS vars from `@pekulo/ui/generated.css`.
- **Rule:** When styling input/button/form-element via `styled.<el>()`:
  - Use Tamagui style options for box-model (size, padding, margin, border, background, position, flex).
  - Use inline `style={...}` for text-style (color, fontSize, fontWeight, outline, letterSpacing) referencing theme CSS vars.
  - Or escalate to a custom Pekulo\*Input primitive in `@pekulo/ui` if reused enough (currently only one consumer — auth-form — so inline is fine).

### 2026-05-04 — Bun `--frozen-lockfile` in Docker requires every workspace member's package.json (Scope: aped-arch, aped-story, aped-dev — stories 0-3, 0-8, every apps/\* Dockerfile)

- **Date:** 2026-05-04
- **Mistake:** Story 0-3 T8 Dockerfile (`apps/api/Dockerfile`) copied only `packages/tsconfig` + `apps/api/package.json` before `RUN bun install --frozen-lockfile`. Verified during T10 (Docker build smoke): the build failed at the install step with `error: lockfile had changes, but lockfile is frozen` even though `bun install --frozen-lockfile` succeeded locally with no changes. Root cause: Bun's frozen install reads the root `package.json` `workspaces` glob (`["apps/*", "packages/*"]`) and requires every workspace member's manifest to be present in the install root — otherwise the lockfile (which records all workspaces) is considered out-of-sync with what's reachable. Locally every workspace exists, so it works ; in the Docker context only `apps/api/` was copied. Compounded by `.dockerignore` excluding `apps/web` wholesale, so even adding `COPY apps/web/package.json` to the Dockerfile would have failed silently (file not in context).
- **Correction:** Two changes locked in for every apps/\* Dockerfile in this monorepo:
  1. **Copy every workspace manifest** before `bun install --frozen-lockfile`. For apps/api this means: `COPY apps/api/package.json apps/api/` + `COPY apps/web/package.json apps/web/` + `COPY packages packages` (the entire packages/ tree is ~92 KB, all 7 members copied at once is fine). apps/prices is Python (no package.json) — Bun's glob silently skips it.
  2. **`.dockerignore` exception for foreign workspace manifests** — `apps/web` exclusion stays (we don't want 2 GB of Next.js sources in the apps/api build context), but add `!apps/web/package.json` immediately after to re-include just the manifest. Same pattern for any future apps/\* that aren't the build target.
- **Rule:** When writing a per-app Dockerfile in a Bun workspace monorepo, the install step must be reachable from a workspace-complete view. Default checklist: (a) every member of the workspaces glob has its package.json copied (or stubbed), (b) `.dockerignore` re-includes those manifests via `!path` exceptions when broader excludes are in place, (c) `RUN bun install --frozen-lockfile` is the gate — if it fails with "lockfile had changes", check workspace coverage _before_ assuming the lockfile is wrong. Apply to story 0-8 (CI/CD) when the GitHub Actions job builds the apps/api image, and to every future apps/\* (mobile build, etc.) that ships a Dockerfile.

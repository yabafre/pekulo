- **Bridge API surface (verified via context7 `/websites/bridgeapi_io` on 2026-05-27 — overrides any LLM training memory):**

  - **Transactions endpoint:** `GET /v3/aggregation/transactions?limit=N&since=<ISO updated_at>`. The `since` parameter (highest `updated_at` from previous batch, stored as `lastRefreshedAt` on the `BankConnection` row) is THE dedup mechanism — Bridge returns only transactions with `updated_at > since`.   - **Webhook signature verification (NFR-33 — CRITICAL):**
    - **Header:** `BridgeApi-Signature: t=<ts>,v1=<hex>,v1=<hex_during_rotation>` — multiple v1 entries during rotation.
    - **Algorithm:** HMAC-SHA256, key = endpoint signing secret, **message = raw event body** (never parsed JSON — must preserve exact bytes incl. whitespace).
    - **Comparison:** timing-safe (Bun `crypto.timingSafeEqual(Buffer.from(expected, "hex"), Buffer.from(received, "hex"))`). Disregard non-v1 schemes (downgrade-attack defense).
    - **Secret rotation:** previous secret valid for 24h, max 2 active. Env keys: `BRIDGE_WEBHOOK_SIGNING_SECRET` (current) + `BRIDGE_WEBHOOK_SIGNING_SECRET_PREVIOUS` (rolled). Verifier tries both during overlap.
    - **Raw body capture:** Elysia route declared so the body is NOT auto-parsed — verify in step 04 which Elysia API yields the raw buffer (`onParse` hook is the leading candidate).
    - **Reject within 100 ms:** mismatch → 401 + early return (no DB query, no payload in logs).
  - **Webhook events of interest:** `item.refreshed` (carries `status_code`, `status_code_info`, `authentication_expires_at`, `full_refresh`, `refresh_trigger: connect|scheduler`). `status_code === 1010` → flip `BankConnection.status = 'sca_required'` (5-7 surfaces). `status_code === 0 && refresh_trigger === 'scheduler'` → trigger Pekulo transaction-fetch sync.

- **Token storage decision (NFR-31 — DEFERRED to step 04 / aped-discuss-epic):**
  - **Option A (recommended):** Supabase Vault (`supabase_vault` extension — validated in Supabase Postgres docs as of 2026). libsodium-backed; access via `vault.create_secret(...)` + `select decrypted_secret from vault.decrypted_secrets where id = ?`. Pros: least crypto code in Pekulo's surface; key derivation handled upstream. Cons: extra extension, foreign table reads.
  - **Option B:** Column-level pgcrypto. `CREATE EXTENSION pgcrypto`; `pgp_sym_encrypt(token, $KEY)` on write, `pgp_sym_decrypt(cipher, $KEY)` on read via Prisma `$queryRaw`. Pros: explicit, well-known. Cons: key rotation = re-encrypt every row; key lives in env.
  - **Option C:** Application-layer (Bun `crypto.subtle`) AES-256-GCM. Pre-encrypt before Prisma write; decrypt after read. Pros: rotation via decrypt-old + encrypt-new migration; key in env. Cons: first Pekulo-side crypto surface; more code to audit.
  - **Universally forbidden:** raw tokens in pino/console logs, OTel span attributes, error messages, error envelopes returned to apps/web, debug dumps, test fixtures committed to git, JSON responses from ANY oRPC handler.

## Previous stories — outcomes

### Story 5-5-monthly-signoff — done 2026-05-27T12:00:00Z

- **Decisions:**
  - **`signOff` is atomic by a single Prisma `upsert` round-trip** — the repository's `upsertByMonth(userId, input, opts?: { signedOffAt?: Date })` folds the freeze stamp into the same Prisma write. Future stories that introduce concurrent-writer scenarios (e.g. V2+ shared accounts, V1+ cron auto-close) MUST keep this single-write shape or upgrade to an explicit `$transaction`; the prior sequential `upsert + setSignedOffAt` was the bug aped-review F1 caught.
  - **Already-signed precedence wins over close-window check in `signOff`** (review F5). For a month that's both already-signed and outside its window, `MONTHLY_SIGNED_OFF` is returned — the more actionable error. Order matters: `findByMonth` first, then window check.

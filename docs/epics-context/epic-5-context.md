## Architecture references

- Patterns to respect:
  - **Module shape (architecture Phase 3 Code Structure):** `apps/api/src/modules/transactions/{transactions.module.ts, transactions.routes.ts, transactions.service.ts, transactions.repository.ts, transactions.errors.ts}` + co-located `*.test.ts` siblings (`*.repository.test.ts`, `*.service.test.ts`, `*.module.test.ts`, `*.integration.test.ts`). **Zero `*.types.ts`** (L1 invariant — every domain type in `@pekulo/types`).
  - **Folder-by-domain in packages (R11 — PR #86 audit codification):** the transactions slice already follows the post-audit layout:
    - `packages/validators/src/transactions/transactions.schemas.ts` + `packages/validators/src/transactions/index.ts` (✓ exists, brownfield-port of the legacy `apps/web/src/lib/schemas/transactions.ts`)
    - `packages/contracts/src/transactions/transactions.contract.ts` + `packages/contracts/src/transactions/index.ts` (✓ exists, empty `{} as const` scaffold)
    - `packages/types/src/transactions/transactions.types.ts` + `packages/types/src/transactions/index.ts` (**NOT YET** — story 5-1 creates this; today the types live inline in the legacy validators file)
  - **Layer separation (ADR-0010):** Component → Hook → Server Action → oRPC client → Elysia handler → service → repository → Prisma. The chain is hard-bounded; 5-1 is API-only (no UI work — see Decisions deferred below).
  - **`@pekulo/zod` SOLE zod entry point (R1):** NEVER `import { z } from "zod"`. Always `from "@pekulo/zod"`. Already applied in `transactions.schemas.ts`; preserve when extending.
  - **Defense in depth (ADR-0013):** `apps/api` connects via Supabase service role (bypasses RLS); explicit `where: { userId }` on every Prisma query is the primary guard; Postgres RLS is the safety net. Lint rule `pekulo/no-prisma-query-without-user-id` blocks omissions. The `prismaIdentifier: ["prisma","tx","client"]` override is already in `.oxlintrc.json`.
  - **Cross-aggregate guard for `accountId`:** transactions reference an account; every create/update verb that accepts an `accountId` MUST pre-flight `accountsRepository.findAccountForUser(userId, accountId)` and surface `ACCOUNT_NOT_FOUND` → 404 when missing. This mirrors story 3-1's lot → holding pre-flight and 4-1's mortgage → realestate pre-flight. The transactions module factory takes `accountsRepository` (or a thin `AccountOwnershipProbe` interface, L1-friendly) as a `RealOwnershipReader` dep.
  - **Prefixed IDs (ADR-0012):** `Transaction → "tx"` is the canonical prefix (architecture L115). **Currently NOT registered** in `apps/api/src/database/id-prefixes.config.ts` — 5-1 registers it. Prisma model `Transaction { id String @id }` has no `@default` → the prefixed-ids extension injects `tx_<base62>` on insert. The repository `create` branch needs the `as unknown as Parameters<typeof tx.transaction.create>[0]["data"]` bridge (mirrors 2-1 / 3-1 / 4-1 precedent — Prisma's generated types require `id` when the column has no `@default`).
  - **Validator boundary (post-port):** the existing `transactionInputSchema` uses `z.string().uuid()` for `id` — relic of the brownfield UUID column. After the prefixed-ID port lands (5-1), `transactionIdSchema` and any input that accepts an existing id MUST shift to `z.string().regex(/^tx_[0-9A-Za-z]{21}$/)`. **This is a contract change**; old UUIDs in the brownfield row population will need a one-time migration (decision deferred — Alex's V1 (a) is single-user, so a wipe-and-replay is acceptable per the personal-use phase).
  - **Decimal → number boundary (L24):** `amount` is `@db.Decimal`. Every row → DTO must coerce via `decimalToNumber(value, fallback)` from `apps/api/src/common/derive/decimal-to-number.ts`. NEVER `Number(decimal)` (lessons.md scope list explicitly names story 5-1).
  - **`Elysia` type is invariant (L8 — 2026-05-04 lesson explicitly names story 5-1 in scope):** never annotate variables/parameters as bare `Elysia`. Use inferred return types on the module factory (`ReturnType<typeof createTransactionsRouter>`); accept `AnyElysia` at any cross-cutting boundary.
  - **Pagination convention (D2):** the transactions list endpoint MUST use cursor-based keyset pagination `(occurredOn desc, id desc)` (NOT `createdAt desc` — transactions are ordered by `occurredOn` per the brownfield index `transactions_user_date_idx`). Response shape: `{ items: Transaction[], nextCursor: string | null }`. The brownfield index `(user_id, occurred_on desc)` already supports this.
  - **oRPC routing convention:** kebab-case, resource-oriented, plural on resources. Non-CRUD actions use an explicit verb at the end of the path (e.g. `/transactions/import-csv` for 5-2, `/transactions/categorise` for 6-2). Mount path: `/rpc/v1/transactions` (already declared in `packages/contracts/src/transactions/transactions.contract.ts` meta).
  - **Categorise pipeline shape (forward-pointer for 5-3 / 6-2):** `transactions.service.categorise(tx)` is the single entry point that (a) runs the pure `derive/transfer-rule.ts` first (5-3); (b) on miss, delegates to the LLM router `llm.service.categorise(tx)` (6-2). 5-1 does NOT wire `categorise` — it ships the manual record path (`create`, `update`, `delete`, `list`, `get`) only. The contract leaves a hole for `categorise` to be added in 5-3 sub-tree-versioned at `/rpc/v1/transactions` without a major bump.
  - **Cache invalidation graph (forward-pointer for 5-2/5-3/5-4/5-5/6-2/7-1):** wire `transactions` invalidation tag into `apps/web/src/lib/zapaction/keys.ts` `setTagRegistry({...})`. The tag must include cross-edges to `accounts` (a transaction affects the cash balance) AND `dashboard` (total wealth re-aggregates). Story 5-4 / 5-5 will add `monthly` cross-edges; 6-2 will add `llm` cross-edges. Mirror story 4-1 T18 forward-pointer.
  - **Error envelope discipline (lessons.md 2026-05-20 — "defineAction + discriminated-union output"):** when 5-X UI stories ship server actions that return `{ ok: true; ... } | { ok: false; code; message }` envelopes, the `defineAction({ output: ... })` slot MUST be omitted. zapaction core runs `output.parse(result)` unconditionally and rejects the error branch. Belongs to UI stories, not 5-1 — flagged here so future authors don't re-introduce the regression.

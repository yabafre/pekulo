### 2026-06-15 — A decorative full-area `<canvas>` animation must be cheap BY DEFAULT: pin render to 1 device pixel, throttle to ~30fps, and pause while the tab is hidden — otherwise it pegs the browser renderer AND WindowServer (compositing a full-panel repaint every frame). Story 8-1's cloudvault-style `FallingPattern` shipped as an unthrottled ~60fps loop at `devicePixelRatio` 2, `fill`+`putImageData` over the whole right-half buffer + ~100k `Math.sin`/frame → measured ~24% renderer + ~48% WindowServer on the auth screen. (Scope: aped-dev, aped-review — every decorative canvas/rAF animation)

- **Date:** 2026-06-15
- **Mistake:** Ported the FallingPattern canvas faithfully (60fps, dpr-2, per-frame full-buffer blit) for the auth split-screen. It looked great but heated the CPU; the user flagged it. First, MEASURED before guessing (lesson 2026-06-03): `ps -Ao pcpu,comm -r` showed the Arc renderer + WindowServer hot while the bun dev server was idle (react-grab already CDN-global) — so it was the browser animation, not Turbopack.
- **Correction:** It is a background, so make it nearly free: `RENDER_DPR = 1` (4× fewer pixels to fill/blit), throttle the rAF loop to ~30fps (`ts - last < FRAME_MS` skip — the field drifts slowly so 60fps is imperceptible), pause entirely on `document.hidden` (visibilitychange), and widen the dot grid (gap 6→8). ~8–14× less main-thread + compositing work, visually unchanged. Commit `4228c8f`.
- **Rule:** Decorative whole-area canvas/rAF effects default to: dpr 1 (retina density is wasted on a faint background), an explicit fps cap (24–30 is plenty for ambient drift), and a visibility/IntersectionObserver pause so they never animate offscreen. Diagnose any "X heats the CPU" by measuring which PROCESS is hot (renderer/WindowServer = browser paint vs dev-server = bundler) before touching code. `aped-review` flags any unbounded rAF loop that repaints a large surface every frame at full dpr.

### 2026-06-15 — A custom oxlint JS-plugin rule that self-gates on `context.filename` is silently INERT when its path anchors don't match how the linter feeds filenames — and a green lint is NOT proof the rule ran. `no-server-action-in-component` anchored `componentRoots` on `apps/web/src/…`, but `oxlint src` runs from `apps/web` and `normaliseFilename` strips the cwd, so `context.filename` arrives as `src/components/…` → `isComponentFile` matched zero files and the rule fired on nothing (since it was written). It had been dead the whole time; the story 8-1 review only found it because an auditor probed it with a known-bad fixture. (Scope: aped-dev, aped-review, aped-claude — every custom oxlint rule that self-gates on filename; verify activeness with a deliberately-violating fixture, never infer it from a green run)

- **Date:** 2026-06-15
- **Mistake:** aped-review tried to "close a blind spot" in `no-server-action-in-component` (it only matched the global `@/lib/actions/` root, not per-feature `_actions/`). The widening + an `allow` option + new RuleTester cases all passed `bun test` — but RuleTester feeds repo-root-relative filenames (`apps/web/src/...`), whereas production `oxlint src` (run from `apps/web`) feeds cwd-relative ones. So the unit tests were green AND the production rule was inert: a probe component importing `@/lib/actions/...` was never flagged. Naively fixing the anchoring then surfaced a _legitimate_ RSC server-to-server call (`bank/callback/page.tsx`) as a false positive, because the rule has no `'use client'` gate.
- **Correction:** Reverted the rule/config/test to their `main` state (the proper hardening — cwd anchoring + `'use client'` gate + a per-feature allowlist for the documented `(auth)/_actions/` exception — is lint-infra scope, not an auth story; tracked in #135). Kept the in-scope fix: documented the auth direct-call exception in `architecture.md` and recorded the enforcement gap there. The auth components legitimately call `auth-actions.ts` directly (Supabase SDK, no React Query cache).
- **Rule:** A custom lint rule's filename matching MUST be invocation-aware: RuleTester and `oxlint <dir>` can hand it different path roots (repo-root vs cwd-stripped). Anchor on cwd-relative paths (or normalise to one canonical form) AND prove the rule is live with a committed deliberately-violating fixture — a passing unit suite proves the rule's _logic_, not that it _runs_ on real files. For component/action boundary rules specifically, gate on `'use client'`: RSCs calling server functions directly are legitimate and must not be flagged. `aped-review` MUST, for any change to a self-gating lint rule, drop a known-bad fixture into the real tree and confirm `run lint` flags it before trusting "lint green = compliant".

### 2026-06-15 — Supabase's `amr` (Authentication Methods References) claim does NOT carry a `"recovery"` method (auth-js `AMRMethods` = password/otp/oauth/totp/mfa._/anonymous/sso.saml/magiclink/web3/oauth_provider._), so a server-side SSR app with httpOnly cookies CANNOT tell a password-recovery session from a normal full session by reading `getClaims()`/`amr`. The canonical client signal (`onAuthStateChange` `PASSWORD_RECOVERY` event) is unavailable server-side. The robust fix is a server-set marker: the auth callback writes a short-lived httpOnly cookie ONLY after a verified `exchangeCodeForSession` whose `next` is the recovery page, and the page trusts that marker (not mere session presence) to enter reset mode. (Scope: aped-dev, aped-arch, aped-review — any server-side recovery/step-up flow that must distinguish a special session from a normal one under httpOnly cookies)

- **Date:** 2026-06-15
- **Mistake:** Story 8-1's `/recover` page used `mode={user ? "reset" : "request"}` — so ANY authenticated user reaching `/recover` (manual URL) saw the set-new-password form, because `getUser()` returns a user for both a recovery session and a full session. The first instinct at review was to gate on `amr` containing `recovery` — but inspecting the installed `@supabase/auth-js@2.104.1` types showed `recovery` is not in `AMRMethods`; relying on it would have either never entered reset mode (breaking the real recovery happy-path / AC-4) or silently failed.
- **Correction:** The callback sets `pekulo-pwd-recovery` (httpOnly, sameSite=lax, maxAge 600s, set on the redirect response) only when `exchangeCodeForSession` succeeds AND `next === "/recover"`; the RSC reads it (no session → request mode; session + marker → reset; session + no marker → bounce to `/dashboard`); `updatePassword` deletes it on success. A single shared `RECOVERY_MARKER_COOKIE` constant prevents setter/reader typo drift. Unit tests cover clear-on-success / keep-on-failure; the page gate rests on manual verification (no RSC harness).
- **Rule:** Before gating a server-side flow on a Supabase claim (`amr`, `aal`, custom), confirm the exact value exists in the installed `auth-js` types — `amr` has no `recovery` method, and a wrong gate on a recovery/step-up path silently breaks the legitimate user, which is worse than the over-permissive bug it tries to fix. For "distinguish a special session from a normal one under httpOnly cookies", set a deterministic server-only marker at the verified transition point rather than inferring intent from claims. Always factor the cookie name into one shared constant.

### 2026-06-05 — Every new Prisma model with a CREATE path must be registered in `id-prefixes.config.ts` (a prefix, or `null` to opt out for natural-key/`user_id`-PK tables) — because the `prefixed-ids` extension (ADR-0012) fires on EVERY `create`/`upsert` and throws `MissingPrefixError` for an unregistered model, and STUBBED repo/service unit tests never load the extension, so a missing registration ships as a runtime **500 on the first write** while every test stays green. 2nd occurrence: 6-10's logo caches, now 7-2's `dashboard_layout` (`saveLayout` upsert 500'd in prod while `getLayout` was 200 — only the create branch hits the extension). (Scope: aped-dev, aped-review — every story that adds a Prisma model)

- **Date:** 2026-06-05
- **Mistake:** Story 7-2 added the `DashboardLayout` model (PK `user_id`, no synthetic id) but did not register it in `ID_PREFIXES`. Typecheck passed (the generated client has the model); the dashboard service/repository/integration tests passed (they stub the repository or `prismaService`, so the real `prefixed-ids` extension never runs). The gap only surfaced at runtime: `getDashboardLayout` returned 200 (SELECT has no create branch) while `saveDashboardLayout`'s `upsert` → `create` threw `MissingPrefixError` → 500. Compounded by a SECOND deferred step — the hand-authored migration was never `migrate deploy`'d to the dev DB, so the table was missing too (a separate 500 on the read, fixed first).
- **Correction:** Registered `DashboardLayout: null` (same opt-out shape as `BridgeUser` + the logo caches — `user_id`/natural-key PK, no id injection), reproduced the real upsert against the live DB to confirm GREEN, and tightened `id-prefixes.config.test.ts` (count 21→22 + the key list + a `getPrefix("DashboardLayout")` null assertion). Applied the pending migration via `prisma migrate deploy`.
- **Rule:** Adding a Prisma model is THREE inseparable steps, not one: (1) the schema + migration, (2) **register the model in `id-prefixes.config.ts`** (a prefix for synthetic-id tables, `null` for `user_id`/natural-key PKs), (3) `migrate deploy` to actually create the table. A green unit suite is NOT evidence the write path works when the repository is stubbed — exercise the real `create`/`upsert` once (a throwaway script against the dev DB, or an integration test with a real client) before declaring done. The cheap class-killer is a meta-test that enumerates the Prisma DMMF models and asserts each appears in `ID_PREFIXES`; `aped-review` MUST, for any new model, confirm the `ID_PREFIXES` entry AND a real (non-stubbed) create has been exercised.

### 2026-06-04 — A cross-domain aggregator that composes a SIGNED derived value into a downstream pure helper with a domain precondition (`>= 0`, `> 0`, non-null) silently breaks for any user in the out-of-range state UNLESS it clamps/guards at the composition boundary. Story 7-1's `dashboard.getOverview` summed real-estate equity RAW into `totalWealthEur` and fed it straight to `compass-progress.computeProgress`, which throws `CompassError("INVALID_WEALTH")` for `currentWealth < 0` (→ HTTP 400). Net wealth CAN go negative (underwater property: debt > valuation, exceeding cash + holdings) — and the producing helper `property-equity.ts` _literally pre-warned_ this in its header ("Underwater properties return a negative number; the caller decides whether to display it raw or clamp to zero — the dashboard total-wealth aggregator in story 7-1 will sum raw values"). The module's own header claimed "getOverview NEVER throws", yet it did. (Scope: aped-arch, aped-dev, aped-review — every cross-domain aggregator/composition that feeds a composed value into a helper carrying a sign/range/non-null precondition)

- **Date:** 2026-06-04
- **Mistake:** `dashboard.service.getOverview` computed `totalWealthEur = snapshot.kpi.capitalTotal + equity.totalEquityEur` and passed it unclamped as `computeProgress({ currentWealth: totalWealthEur, ... })`. A compass-having user whose net real-estate equity is negative enough to drive total wealth below zero got a 400 instead of an overview — contradicting AC-3 ("does not error"), the module's "never throws" contract comment, and the NFR-18 graceful-degradation spirit. The 814-test suite was green only because every fixture used `+250 000 €` equity; no fixture exercised negative net wealth. Two independent aped-review auditors (Code + Edge) converged on it; the Lead reproduced it with a throwaway stub before fixing. The graceful-fallback design existed only on the PRICE path (`priceHoldings` try/catch), never on the compass-progress path.
- **Correction:** Clamp at the boundary — `currentWealth: Math.max(0, totalWealthEur)` into `computeProgress`, while the RAW `totalWealthEur` still ships in the payload (the hero shows the real negative; an underwater user reads 0 % progress against the full gap, never an error). Also degraded a failed `getCompass` read to `null` (compass is optional) instead of 500-ing the whole overview — but deliberately LEFT the three wealth-bearing reads (accounts/holdings/equity) throwing, because a finance dashboard must never silently under-report net wealth. Added regression fixtures for negative equity + the dedup/degradation paths. Commit `150cfed` during aped-review.
- **Rule:** When an aggregator composes a SIGNED or nullable value into a helper that carries a domain precondition, clamp/guard at the composition boundary — never assume the upstream value is in range. Read the producing helper's header contract first: if it says "returns negative; caller clamps" (as `property-equity.ts` did), the clamp is the consumer's job, by design. A "never throws" promise on a read endpoint is only true when EVERY downstream call's preconditions are guaranteed by construction or explicitly guarded — audit each composed term, not just the obvious one (the price path was guarded; the compass path was the gap). `aped-review` MUST, for any cross-domain aggregator, enumerate each composed value's sign/range/nullability and confirm a clamp/guard precedes any precondition-bearing helper; a missing guard on a signed/nullable input is a [MAJOR]. Always pair the fix with a fixture exercising the out-of-range case (negative equity, empty list, null source) — an all-positive happy-path fixture hides the entire class.

### 2026-06-03 — A sustained-CPU symptom on a Next DEV page (fan pegged ~7 cores, "only this page, since the last story") that LOOKED like a React remount/refetch loop was actually `react-grab` LOADED THE WRONG WAY — as a Turbopack-bundled `import("react-grab")` instead of its pre-built CDN global build. The bundled import makes the dev server BUNDLE the whole large instrumentation library AND generate its per-component source-maps, which on the heaviest route pegs `next` to ~7 cores; the pinned `index.global.js` IIFE (react-grab's official Next.js pattern) runs entirely in the BROWSER, outside the bundler → dev server idles at 0% with react-grab fully working (hover + ⌘C). The fix is the LOADER, not gating the tool off. (Scope: aped-debug, aped-dev, aped-review — any "page X pegs the CPU" on a Next dev build; load whole-tree dev inspectors as a CDN global, never a bundler import)

- **Date:** 2026-06-03
- **Mistake:** A user reported `/dashboard/transactions` pegging the Next dev server at ~391% then ~747% (≈7 cores), "only this page, new since story 6-7". Dev logs (repeated `GET /dashboard/transactions` at `application-code: 6.1s`, queries re-firing no-month → month) looked exactly like a Server-Action → route-revalidation → `<Suspense>` re-suspension → subtree REMOUNT → cache-loss → re-fetch loop, so I generated 5 ranked hypotheses around remount and nearly refactored the 6-9 Suspense/provider structure (lesson 2026-05-26). Mount counters falsified all of them; I then jumped to a SECOND wrong conclusion ("one-time Turbopack/Tamagui dev-compile, it settles") — but the fan kept blowing; then to a THIRD half-measure (gate react-grab off behind `NEXT_PUBLIC_REACT_GRAB`) — which the user rightly rejected: turning the tool off is not fixing the overheat.
- **Correction:** `sample <next-pid>` on the live `next` process showed the main thread parked in `kevent64` (event-loop wait) with the cores on Bun WORKER threads → dev-server work, not app rendering (which had settled to MOUNT #1). Bisected the one heavy dev-only thing loaded site-wide: commenting `<ReactGrabDev>` out of `app/layout.tsx` calmed the fan instantly. Root cause: `react-grab-dev.tsx` did `void import("react-grab")`, so Turbopack pulled the entire react-grab library + its source-map resolution through the dev server (the worker-thread CPU), and the 6-7 auto-apply (341 rows now rendered in Récentes) tipped the heaviest route over the edge → "since 6-7 / only this page". Real fix: load react-grab's PINNED CDN global build (`https://unpkg.com/react-grab@0.1.44/dist/index.global.js`, injected client-side, dev only) — an IIFE that runs outside the bundler, so the dev server does zero react-grab work. Verified: `next` back to **0.0% CPU** with the transactions page open + react-grab working. Version is pinned (no `@latest`) and `unpkg` is allowed in the dev CSP only (`headers.ts`). Two real secondary issues also fixed: invalid `borderRadius: "$3"` in `PekuloPagination` (named radius scale `none/sm/md/lg/xl/full` → warn + fallback every render) → `$md`; and a load-time DOUBLE-FETCH (month-scoped reads fire once unscoped while `MonthScopeProvider` resolves the active month, then re-fire scoped) → `enabled: month != null` gate on `useTransactions`/`usePendingSuggestions` + a regression test (`transactions-month-gate.test.tsx`).
- **Rule:** Load any heavy whole-tree dev inspector (react-grab, react-scan, why-did-you-render) as its PRE-BUILT CDN GLOBAL (`index.global.js` IIFE injected as a `<script>`), NEVER a bundler `import()` — a bundler-resolved import makes the DEV SERVER bundle the library and generate its source-maps, which on a heavy route pegs it to many cores (browser-side runtime cost is separate and unavoidable, but the dev-server cost is pure self-harm). To diagnose a "page X pegs the CPU" symptom: (1) mount-counter the suspect provider(s) — stuck at #1 kills the remount/Suspense-refactor reflex; (2) `sample <pid>` the actual process (PID from `lsof -iTCP:<port>`) — main thread in `kevent64` + busy WORKER threads = dev-server/bundler work, not app render → bisect dev-only instrumentation by commenting it out of the layout; (3) "it's just dev-compile" holds only if the CPU SETTLES — sustained ≠ compile; gating the tool off is a workaround, fixing how it loads is the solution. And gate provider-resolved-scope child queries (`enabled`) against load-time double-fetch.

### 2026-06-02 — Bulk-import auto-categorisation needs an EXPLICIT origin signal (a `source` column), because a CSV-imported row and a hand-typed row are indistinguishable by `provider` alone (both NULL). Story 6-7 makes bulk rows (csv/bridge) AUTO-APPLY the LLM category as the final `category`, while interactive (`manual`) rows keep the 6-4 suggestion→confirm flow — but the SAME global backlog sweep (`backfillSuggestionsImpl`) categorises both. Without a per-row origin it cannot decide apply-vs-suggest, so it would either suggest for everything (auto-apply dead) or auto-apply for everything (silently overwriting interactive rows the user wanted to confirm). (Scope: aped-arch, aped-dev, aped-review — any policy that must branch on "where did this row come from" when the existing columns can't tell two origins apart)

- **Date:** 2026-06-02
- **Mistake:** N/A — design decision recorded up-front (story 6-7 step-04), not a shipped bug. The trap it avoids: reusing `provider IS NULL` (or `category === 'autre'`) as a proxy for "manual origin" — `provider` is NULL for BOTH a CSV import and a hand-typed row, so a sweep keyed on it would auto-apply CSV rows correctly but ALSO auto-apply any interactive row whose inline suggestion missed, defeating AC-3 (the interactive confirm flow).
- **Correction:** Added a server-internal `transactions.source` column (`'manual' | 'csv' | 'bridge'`, plain TEXT, no CHECK — universe enumerated in `@pekulo/validators#TRANSACTION_SOURCES`, mirrors the free-String `category`). The repository stamps `csv`/`bridge` on the two bulk-insert paths; `listAutreWithoutAttempt` surfaces `source`; `backfillSuggestionsImpl` branches: `manual` → `saveSuggestion` (pending), bulk → `applySuggestedCategory` (final category, suggested\_\* kept as provenance). `source` stays out of the public DTO — the web "· IA" hint derives from `category === suggestedCategory`.
- **Rule:** When a behaviour must branch on a row's ORIGIN (manual vs imported vs synced) and the existing columns can't distinguish the origins (a NULL `provider` collapses CSV + manual), add an explicit origin/source column rather than overloading a proxy column. Keep it server-internal unless a client genuinely needs it (derive client-visible state from already-exposed fields). A global sweep that applies an irreversible policy (auto-apply, auto-delete, auto-merge) MUST read the origin signal before acting; `aped-review` flags any backlog/sweep that infers origin from a proxy column shared by two origins.

### 2026-06-02 — Numbered (offset) pagination is an ACCEPTABLE, documented deviation from D2 ("offset forbidden for transactions") for a BOUNDED, numbered-page UI view — a cursor cannot serve "page N" (random access) and PekuloPagination needs a `totalCount`. Story 6-9 ext gave the Récentes list numbered 10/page like the Suggestions IA list; both opt into an offset path (`page?` → `skip/take + count`) while the cursor path stays the default for every other caller. The deviation is safe only because the view is small at Persona #1 scale (≤ a few hundred rows); at the NFR-16 50k cap offset gets slow and must revert to cursor next/prev. (Scope: aped-dev, aped-review — any list UI that needs random-access numbered pages; keep offset opt-in + bounded + documented, never the default for an unbounded user-data list)

- **Date:** 2026-06-02
- **Mistake:** N/A — deliberate, user-approved deviation (not a bug). Recorded so the next "add pagination here" doesn't either (a) blindly clone offset onto an unbounded list (D2/NFR-16 violation at scale) or (b) assume cursor pagination can do numbered pages (it can't).
- **Correction:** `listTransactions` gained an opt-in `page?` (offset: `skip/take + totalCount`); absent `page` = cursor (default). Récentes uses `?page` (nuqs) + PekuloPagination, 10/page. Documented in architecture D2 (the exception list), the 6-9 story Extension, and the epic-6 cache.
- **Rule:** Cursor pagination = the default for user-data lists (D2). Reach for offset ONLY for a bounded, numbered-page view, make it opt-in (a `page?` field, not a mode swap), always return a `totalCount`, and document the deviation in architecture D2 + the owning story. `aped-review` flags any NEW offset path on a potentially-unbounded list that isn't justified by a documented bound.

### 2026-06-02 — Supabase's `rls_disabled_in_public` advisor flags EVERY public-schema table reachable via the auto-generated PostgREST API — including no-PII reference/cache tables that the in-repo `rls-migration-audit` deliberately exempts via `NON_USER_TABLES`. The two gates measure different things: the static gate asks "does a USER-DATA table have RLS + policies?" (and skips allow-listed non-user tables); Supabase's live advisor asks "can the anon role reach this table at all?" — and the answer is yes for any `public` table without RLS, PII or not. Story 6-10's `merchant_logo_cache` / `provider_logo_cache` (plus Prisma's own `_prisma_migrations`) tripped the advisor even though the internal gate was green. (Scope: aped-dev, aped-review — every public reference/cache/internal table; reconcile the internal RLS gate with the Supabase advisor before declaring RLS coverage complete)

- **Date:** 2026-06-02
- **Mistake:** The logo caches shipped (6-10) with RLS DISABLED by design ("no user data → no RLS"), allow-listed in `rls-migration-audit`'s `NON_USER_TABLES`. The internal static gate passed, so RLS was considered "covered" — but Supabase's database linter (`0013_rls_disabled_in_public`) still raised ERROR on `merchant_logo_cache`, `provider_logo_cache` AND `_prisma_migrations`: all three are anon-reachable via PostgREST, a write/poison + metadata-leak surface regardless of PII.
- **Correction:** Migration `20260602150000` runs `ALTER TABLE … ENABLE ROW LEVEL SECURITY` on all three with **no policies** = deny-all to anon/authenticated; `apps/api`'s service-role connection bypasses RLS (and Prisma migrate uses the same privileged connection), so reads/writes + migrations are unaffected. The two logo tables STAY in `NON_USER_TABLES` because deny-all (0 policies) is intentional, not the ≥ 2 a user-data table needs. Synced architecture.md L131 ("no RLS" → "RLS-on, no-policy"), ADR-0015, `logos.prisma` + the audit comment. The Supabase Auth "leaked password protection" WARN is a dashboard / Management-API toggle (not code) — deferred to the (b) hardening pass alongside MFA / rate-limit (NFR-11).

Every `public`-schema table reachable by PostgREST gets `ENABLE ROW LEVEL SECURITY`; user-data tables add policies, reference / cache / internal tables enable-with-no-policy (deny-all to anon, service-role bypasses). `aped-review` reconciles the internal `rls-migration-audit` allow-list against the Supabase advisor — an allow-listed table must still be RLS-ENABLED, just policy-free.

### 2026-06-02 — A cache row's `fetched_at` that is WRITTEN but never READ is a silent "permanent cache" bug: the TTL / refresh-window the AC promised never elapses, so a once-failed lookup is stuck on the fallback forever. Story 6-10's logo caches stamped `fetched_at` on every upsert, but `resolveMerchantLogo` / `resolveProviderLogo` returned any existing row unconditionally (`if (cached !== undefined) return cached.logoUrl`) — AC-5's "not looked up again before its refresh window elapses" had no window. The "negative-caches a miss" test passed precisely because it only proved the WITHIN-window short-circuit (`calls === 1` on an immediate second lookup); with no injected clock it could never exercise the expiry path. Separately the same aped-review found the whole post-scope-lock 6-10 extension (Brandfetch egress, the `/v1/logos` proxy + web-tier auth-bypass, the `accounts.provider_id` column + migration) shipped without touching `architecture.md` / ADR-0015 / `lessons.md` — the exact desync lesson 2026-05-31 warned about, even though the story's Extension section claimed "doc-synced". ### 2026-06-10 — Soft-delete (revoke) + a stable-key dedup guard = permanent reconnect block (Scope: aped-debug — bank-aggregator story 5-7)

- **Date:** 2026-06-10
- **Mistake:** `revokeConnection` soft-deletes a bank connection (status→`revoked`) and intentionally KEEPS its local `Account` rows (transaction history is preserved). The guard could not tell "account owned by an ACTIVE connection" (a genuine duplicate to block) from "account orphaned by a REVOKED connection" (a legitimate reconnect). Accounts carry no link to their owning connection, so connection status was unreachable from the account.
- **Correction:** Store the Bridge institution `provider_id` on `bank_connections` (migration `20260610130000`, nullable, no backfill) and rekey the guard on it: `completeConnection` now rejects only when `findActiveByProviderId(userId, "bridge", institutionId)` finds a NON-revoked connection for the same institution.

### 2026-05-20 — Hooks under `apps/web/src/app/**/_hooks/` consumed raw `useQuery` / `useMutation` / `useQueryClient` from `@tanstack/react-query` despite ZapAction being fully wired at the action layer (`defineAction`), the context resolver (`setActionContext`), and the tag registry (`setTagRegistry` mapping the full cross-feature graph) ; the registry was effectively inert because no hook ever consumed it, so every mutation invalidated cache slices by hand via `queryClient.invalidateQueries({ queryKey })` (Scope: aped-arch, aped-dev, aped-review — every web-tier hook that reads from / writes to an action ; revisit any inherited hook before adding new ones)

- **Date:** 2026-05-20
- **Mistake:** Stories 1-1 through 3-4 shipped 18 hooks under `apps/web/src/app/(cap)/dashboard/**/_hooks/` that all bypassed ZapAction. They imported `useQuery`, `useMutation`, `useQueryClient` directly from `@tanstack/react-query`. Each mutation hook manually called `queryClient.invalidateQueries({ queryKey: someKeys.x() })` — sometimes invalidating 6 keys in sequence (`use-update-compass.ts` invalidated current + setup + progress + curve + history + milestonesKeys.list). The `lib/zapaction/keys.ts` file declared `createFeatureKeys` / `createFeatureTags` and called `setTagRegistry({...})` with a rich cross-feature edge graph (milestones → compass.setup, portfolio ↔ accounts, holdings → portfolio.holdings + .snapshot). NONE of that ran ; the registry never fired because no `useActionMutation` consumed it. The pattern looked correct because the surrounding wire (actions in `_actions/*.ts` calling `defineAction({ input, tags, handler })`, `setActionContext` in `lib/zapaction/context.ts`) was all by-the-book — every reviewer assumed the hook layer was also ZapAction-shaped without verifying.
- **Correction:** Pekulo policy (PR #86, ZAP-1) — every hook under `apps/web/src/app/**/_hooks/` MUST consume actions via `useActionQuery` (reads, `readPolicy: "read-only"`) or `useActionMutation` (writes, `invalidateOnSuccess: true`) from `@zapaction/query`, or `useAction` from `@zapaction/react` for imperative flows. Direct `useQuery` / `useMutation` imports from `@tanstack/react-query` are BANNED in hooks. `useQueryClient` is allowed ONLY inside `onMutate` / `onError` / `onSettled` of `useActionMutation` for the documented optimistic-update recipe — manual `queryClient.invalidateQueries` in the hook body is a review fail because it bypasses the tag registry.
- **Rule:** Codified as R3 + R4 + R9 in architecture.md Phase 3 "Audit-derived conventions (2026-05-20 — PR #86)". A future custom oxlint rule (`pekulo/no-tanstack-query-in-hook`) will catch the bypass at lint time ; pre-rule, reviewers grep for `from "@tanstack/react-query"` in `apps/web/src/app/**/_hooks/*` on every PR that adds a hook.

### 2026-05-20 — Sub-agents auditing the monorepo on `main` flagged `realestate.prisma` and `holdings.prisma` as CRITICAL missing files even though the realestate work was in flight on `feature/24-4-1-realestate-domain` (T3-T7 committed) and `Holding` / `HoldingLot` models live inside `accounts.prisma` as a sub-aggregate (ADR-0012 carves an aggregate-root exception) ; agent prompts that audit a single branch in isolation produce false-positive "missing" findings whenever the codebase intentionally co-locates aggregate roots OR distributes WIP across feature branches (Scope: aped-arch, aped-review, aped-debug — every audit / sub-agent that reads `prisma/schema/` or `modules/` and reports "missing")

- **Date:** 2026-05-20
- **Mistake:** During the archi-deadcode audit (PR #86), the first Explore sub-agent emitted a CRITICAL finding: "Missing Prisma schema files (ADR-0012 violation) — holdings.prisma, realestate.prisma, llm.prisma, kpis.prisma, dashboard.prisma". The audit was running on a worktree forked from `main`. (a) `realestate.prisma` legitimately doesn't exist on `main` because the realestate domain is in flight on `feature/24-4-1-realestate-domain` (T3 d6b4e0f added the schema there). (b) `holdings.prisma` doesn't exist because `Holding` and `HoldingLot` are declared inside `accounts.prisma` — the `Account → Holding → HoldingLot` aggregate shares a root entity, which ADR-0012's "one .prisma per module" rule was always supposed to accommodate (a co-location exception left undocumented). (c) `llm`, `kpis`, `dashboard` aren't built yet — flagging them as "missing" without checking whether their modules exist conflates "future work" with "violation".
- **Correction:** Audit prompts MUST: (1) check the actual branch state BEFORE flagging missing files — if a domain has a `feature/<n>-<m>-<name>` branch with recent commits, missing schema files on `main` are expected ; (2) check whether the module folder exists under `apps/api/src/modules/` BEFORE flagging the matching `.prisma` — no module folder = no contract violation ; (3) for aggregate-root entities (Account → Holding → HoldingLot), accept the aggregate-shared `.prisma` file as the canonical location and document the exception inline.
- **Rule:** Codified as R10 in architecture.md Phase 3. Sub-agent prompts in `.aped/aped-arch-audit/` (and equivalents) will get a "branch-aware reading + aggregate-root exception" preamble before they scan `prisma/schema/` or flag any missing-file finding.

### 2026-05-20 — `defineAction` with a discriminated-union envelope return type MUST omit `output:` ; zapaction core runs `output.parse(result)` on every handler return, and a Zod schema typed as `{ok: z.literal(true)}` (or any narrow success-only shape) silently rejects the `{ok: false, code, message}` error envelope at the SA boundary so the hook's `result.ok` narrowing path is unreachable in production (Scope: aped-arch, aped-dev, aped-review — every web-tier `defineAction` that propagates typed ORPCError codes through a result envelope)

- **Date:** 2026-05-20
- **Mistake:** Story 3-4 T1's `closeHolding` was authored with `output: closeHoldingOutputSchema` AND a catch block that returned `{ ok: false, code: "HOLDING_NOT_FOUND", message }`. The output schema (`packages/validators/src/holdings.ts:135`) is `z.object({ ok: z.literal(true) })` — only the success branch type-validates. zapaction core (`node_modules/.bun/@zapaction+core@0.2.2.../dist/index.js:138-139`) runs `if (output) { output.parse(result); }` unconditionally on every handler return. On the `HOLDING_NOT_FOUND` path the catch returned an envelope shape Zod rejects with a `ZodError` — the discriminated union never reached `useCloseHolding`, the hook's `result.ok` guard was unreachable, and Next.js sanitised the thrown Error message in prod (the original L25 / 2-3-T2 motivation for envelopes in the first place). The two sibling actions in the same file (`createHolding`, `recordLot`) correctly omitted `output:` ; only `closeHolding` deviated. The bug shipped through aped-dev unnoticed because no test exercised the `HOLDING_NOT_FOUND` path — the 4 a11y test suites only ran axe on initial render with mocked actions. aped-review's Edge & hallucination auditor caught it by reading zapaction's dist + cross-checking the `deleteAccount` precedent in `accounts-actions.ts:95-115` (which intentionally omits `output:` for exactly this reason).
- **Correction:** Drop `output:` on every `defineAction` that can return a discriminated-union envelope on the catch path. The TypeScript return type still pins the contract for callers ; the only thing removed is the runtime Zod check. If runtime validation of the success branch is genuinely needed, validate inside the success leg of the try block (`output.parse(holding)` before `return { ok: true, holding }`) — never on the action's `output:` slot when the action can also return `{ ok: false }`.
- **Rule:** When a web-tier `defineAction` returns `{ ok: true; ... } | { ok: false; code; message }`, the action's `output:` field MUST be omitted. The pattern lives in three places in the codebase as positive precedent: `parametres/_actions/accounts-actions.ts#deleteAccount`, `portefeuille/_actions/holdings-actions.ts#createHolding`, `…#recordLot`. Apply to every future write-path SA across stories 5-X (transactions / monthly), 6-X (LLM categorisation), 7-3 (hypothesis writes), and any new envelope-returning helper. The `aped-review` Edge & hallucination auditor MUST grep for `output:.*Schema` near a `try / catch` block returning `{ ok: false }` ; any match is a [BLOCKER] finding.

### 2026-05-20 — Tamagui `flex: N` only sets `flex-grow` ; without explicit `flexBasis: 0 + minWidth: 0` the wrapper falls back to content-width and the proportional sizing collapses inside a flex-row parent (Scope: aped-dev, aped-review — every apps/web layout that uses `$lg={{ flex: N }}` to share a row between sibling cards)

- **Date:** 2026-05-20
- **Mistake:** Story 3-4 portfolio-section.tsx wrapped the Hero card in `<View $lg={{ flex: 7 }}>` and Répartition in `<View $lg={{ flex: 5 }}>`, inside a parent `<View $lg={{ flexDirection: "row" }}>`. The intent was a 7/5 column split per ux-preview `App.tsx:1461`'s `lg:grid-cols-12` with `lg:col-span-7` / `lg:col-span-5`. CSS `flex: 7` is shorthand for `7 1 0%` (grow, shrink, basis) — but Tamagui's `flex: N` prop only sets `flex-grow`, leaving `flex-basis: auto`. With basis = auto, the wrapper's intrinsic content-width wins the layout negotiation : the Hero card (short text) ended up narrower than the Répartition card (3 ClassRow children), inverting the visual hierarchy. Alex caught it on the live page, not in code review.
- **Correction:** Add `flexBasis: 0` alongside every `flex: N` in Tamagui responsive props, and `minWidth: 0` on the wrapper so the intrinsic content-width doesn't act as a floor. Also add `alignItems: "stretch"` on the parent flex-row so vertical heights match. The full incantation for a proportional split:
  ```tsx
  <View
    flexDirection="column"
    gap="$6"
    $lg={{ flexDirection: "row", gap: "$4", alignItems: "stretch" }}
  >
    <View width="100%" $lg={{ flex: 7, flexBasis: 0, minWidth: 0 }}>
      {/* card 1 */}
    </View>
    <View width="100%" $lg={{ flex: 5, flexBasis: 0, minWidth: 0 }}>
      {/* card 2 */}
    </View>
  </View>
  ```
- **Rule:** Every Tamagui flex-share layout MUST carry `flexBasis: 0 + minWidth: 0` on the children AND `alignItems: "stretch"` on the parent ; otherwise the visual will drift from the spec proportions whenever content lengths differ. Applies forward to every apps/web layout that uses `$lg={{ flex: N }}` — story 4-X immobilier card grid, story 5-X transactions list, story 7-X dashboard bento porting, every future ux-preview port that uses `lg:col-span-N`.

### 2026-05-20 — `@pekulo/ui#Section` (and any primitive that wraps a single Tamagui `<View>` with no height/flex defaults) does NOT inherit `height: 100%` from a flex-row parent's `alignItems: stretch` ; force it via the primitive's `className` escape hatch + a CSS module rule (specificity wins over Tamagui inline styles for `height`) (Scope: aped-dev, aped-review — every apps/web surface that stretches a DS primitive vertically to match a sibling card)

- **Date:** 2026-05-20
- **Mistake:** Story 3-4 wrapped Hero + Répartition in `<Section>` primitives inside a flex-row parent with `alignItems: "stretch"`. The wrapper Views grew to equal heights (good) but the `<Section>` grandchild inside each wrapper stayed at content-height because the primitive's outer `<View>` (packages/ui/src/primitives/Section.tsx:64) ships no height / flex defaults. Result: Hero card was visually shorter than Répartition card despite the wrappers being equal-height — Alex flagged it on the live screen. `alignItems: stretch` only stretches direct children of the row container ; the grandchild Section ignores it.
- **Correction:** Use the `className` prop the primitive exposes to inject `height: 100%` from a CSS module. CSS module specificity wins over Tamagui's inline styles for `height` (which the primitive doesn't set). Created `portfolio.module.css` with `.cardStretch { height: 100%; display: flex; flex-direction: column; }` and passed it to both Section calls via `className={styles.cardStretch}`. Do NOT modify the primitive's defaults — Section is intentionally height-agnostic for the bento cells (which size from grid-auto-rows, not from sibling-stretch).
- **Rule:** When a DS primitive renders inside a flex-row that uses `alignItems: stretch` for proportional vertical sizing, the consumer is responsible for forcing `height: 100%` on the primitive's outer element. The canonical escape hatch is the primitive's `className` prop + a small CSS module. Applies forward to every flex-row layout of `Section` cards across stories 5-X / 7-X. The reviewer (`aped-review`) MUST grep `flex-direction: row` + `Section` and check for a height override on the children.

### 2026-05-20 — `pekulo/no-cross-feature-action-import` lint rule's `featureRoots` default is `apps/web/src/features/` (non-existent in current Pekulo layout) ; it silently no-ops against every App-Router relative import (`../../parametres/_hooks/use-accounts`) so cross-feature boundary checks in `apps/web/src/app/(cap)/dashboard/…` are convention-enforced ONLY (Scope: aped-arch, aped-review — every story that documents an in-code "cross-feature lint guard" comment)

- **Date:** 2026-05-20
- **Mistake:** Story 3-4 portfolio-section.tsx imports `useAccounts` from `../../parametres/_hooks/use-accounts` — a deliberate cross-route hook reference per ADR-0010 (hooks are the orchestration boundary). ### 2026-05-20 — `PekuloSkeleton` was static `opacity: 0.6` until shadcn parity surfaced ; skeleton primitives MUST animate to read as "loading" rather than "empty styled block" — pulse rhythm `1.5s ease-in-out infinite` opacity 0.6 ↔ 0.3 matches shadcn's `animate-pulse` and keeps the TR-strict palette (Scope: aped-arch, aped-dev — every DS primitive that visualises a transient loading state)

- **Date:** 2026-05-20
- **Mistake:** `PekuloSkeleton` (created during story 0-10 / DS migration) shipped with `opacity: 0.6` and no animation. The static block read as a styled empty container rather than as "data inbound" — Alex called it out by comparing with shadcn's `Skeleton` (which uses `animate-pulse`). Static skeletons are technically valid but defeat the affordance they're supposed to carry.
- **Correction:** Added an inline `<style>` keyframes block (`@keyframes pekulo-skeleton-pulse { 0%, 100% { opacity: 0.6 } 50% { opacity: 0.3 } }`) sibling to the View, and applied `animation: pekulo-skeleton-pulse 1.5s ease-in-out infinite` via the View's `style` prop. Keyframes inlined per-instance so the primitive remains zero-dependency on global CSS ; the browser dedupes identical `@keyframes` names across instances. Updated 3 snapshot tests. Same pattern recommended for any future DS primitive that needs a CSS keyframe (e.g. a future ProgressBar indeterminate state, a future Spinner).
- **Rule:** Every DS primitive that visualises a transient loading or in-flight state MUST animate. Static-only skeletons are forbidden — they read as broken UI. The Pekulo animation convention is `opacity 0.6 ↔ 0.3` on a 1.5 s ease-in-out infinite loop, scoped to the `$backgroundMuted` token (TR-strict palette). For primitives needing a fade-in count-up or position transition, the canonical home is `@pekulo/ui/animations` (already used by PekuloDonut, PekuloCountUpEUR, etc.).

### 2026-05-20 — Vitest `vi.mock` factory is HOISTED to module top ; top-level `const mockFn = vi.fn()` then `vi.mock(path, () => ({ x: mockFn }))` fails with `ReferenceError: Cannot access 'mockFn' before initialization` — use `vi.hoisted(() => ({ mockFn: vi.fn() }))` (Scope: aped-dev, aped-review, aped-qa — every web vitest suite that mocks a Server Action factory and needs handler-level reassignment)

- **Date:** 2026-05-20
- **Mistake:** Wrote 3 envelope-narrowing integration tests for story 3-4 (covering `ACCOUNT_NOT_FOUND` / `HOLDING_NOT_FOUND` / `HOLDING_CLOSED`). Started with the pattern `const createHoldingMock = vi.fn(); vi.mock("../_actions/holdings-actions", () => ({ createHolding: createHoldingMock }));`. Tests failed at suite load with `ReferenceError: Cannot access 'createHoldingMock' before initialization`. Vitest hoists `vi.mock(...)` calls to the very top of the file, before any other declaration — the factory ran before the `const` initializer. The earlier `*.a11y.test.tsx` suites in the same folder used bare `vi.fn()` inside the factory (no top-level binding), which is why they worked.
- **Correction:** Use `vi.hoisted` to materialise the mock reference inside the hoisted phase: `const { createHoldingMock } = vi.hoisted(() => ({ createHoldingMock: vi.fn() }));` THEN `vi.mock(path, () => ({ createHolding: createHoldingMock }))`. The hoisted block runs in the same phase as `vi.mock`, so the binding is available when the factory resolves. Same pattern across the 3 new envelope test files.
- **Rule:** When a vitest suite needs to reassign mocked return values per test (`mockResolvedValueOnce`, `mockImplementationOnce`), the mock function MUST be created via `vi.hoisted`, not a plain `vi.fn()` constant. Bare-`vi.fn()`-inside-factory works for render-only tests (no interaction needed) but breaks the moment a test wants per-case behaviour. Belongs forward in every aped-qa skill spec for web integration tests, and as a reviewer-pre-flight for any new `*.test.tsx` that mocks `_actions/*-actions.ts`.

### 2026-05-20 — `fireEvent.click` on a `<button type="submit">` does NOT reliably trigger the parent `<form>`'s `onSubmit` handler in happy-dom (and is fragile in jsdom too) ; use `fireEvent.submit(form)` directly, queried via `getByRole("form", { name: ariaLabel })` (Scope: aped-dev, aped-qa, aped-review — every web vitest suite that exercises a form-submit code path)

- **Date:** 2026-05-20
- **Mistake:** Story 3-4 envelope integration tests filled the create-form fields then `fireEvent.click(getByRole("button", { name: "Ajouter le placement" }))`. The mock action was never called — assertion `expect(createHoldingMock).toHaveBeenCalledTimes(1)` timed out via `waitFor`. happy-dom (and jsdom in older versions) does not fully implement the implicit-submit behaviour where clicking `<button type="submit">` inside a `<form>` fires the form's `submit` event. The on-page `<button>` had `type="submit"` and was inside the form — same as production behaviour — but the synthetic-event simulation skipped the chain.
- **Correction:** Switch to `fireEvent.submit(getByRole("form", { name: "Ajouter un placement" }))` — directly fires the `submit` event on the form element queried by its `aria-label`. The form's `onSubmit` handler runs, validation passes, `mutate(...)` is called, the mock resolves, the envelope-error path runs. Applies to all 3 envelope test suites in `portefeuille/_components/`.
- **Rule:** Web vitest integration tests that exercise a form-submit MUST use `fireEvent.submit(form)`, queried via the form's `aria-label`. The `<button>` query is fine for clicks that aren't a submit (e.g. dialog close, action menu items) ; for submit specifically, the form-level event is the reliable path. Each new form in apps/web ALREADY gets an `aria-label` on its `<form>` element for screen-reader context — that same label is the test selector.

### 2026-05-19 — `bun --filter=<short-name>` needs the workspace package name, not the folder name ; in Pekulo the apps live under `@pekulo/*`, so `bun --filter=api …` exits `No packages matched the filter` ; use `bun --filter=@pekulo/api …` (or `bun --filter='@pekulo/*'` to fan out) (Scope: aped-story, aped-dev, aped-review — every story script that surfaces `bun --filter=<name>` in T-task commands)

- **Date:** 2026-05-19
- **Mistake:** Story 3-3 (`docs/stories/3-3-portfolio-fx.md`) T1/T4/T6/T8/T9/T10 prescribed `bun --filter=api run …`, inherited verbatim from earlier stories that used the same shorthand. The dev tried to run the commands literally and got `error: No packages matched the filter`. The Bun docs state that `--filter` matches against the `package.json#name`, not the folder under `apps/`. In Pekulo every workspace is namespaced `@pekulo/<short>`, so `--filter=api` matches nothing. The dev worked around in-session (`bun --filter='@pekulo/api' …`) but the story prose was not corrected and aped-review caught it as a [NIT] process finding.
- **Correction:** Story commands MUST use the fully-qualified workspace name — `bun --filter='@pekulo/api' run …`, `bun --filter='@pekulo/validators' run …`, `bun --filter='@pekulo/types' run …`. For fan-out across every workspace under the namespace, use `bun --filter='@pekulo/*' run <script>`.
- **Rule:** When aped-story drafts T-task commands that delegate to a workspace, the command MUST use the workspace's `package.json#name` (quoted so the shell does not glob `@pekulo/*` on disk). Reviewers reject `bun --filter=<short>` for any apps/_ or packages/_ under a namespaced monorepo. Apply forward to every Pekulo story 3-4 → 11-X and to any future story-spec audit. Belongs alongside the 2026-05-05 lesson that bans `bun --cwd <relative>`.

### 2026-05-17 — A list/grid using `flex:1 + minHeight:0 + overflowY:auto` to fill a fixed-height parent collapses to 0 height when reparented to a natural-flow column (e.g. a flat mobile stack) ; gate these styles on the `flat` prop OR on a `bento` prop so flat mode uses natural flow (Scope: aped-arch, aped-dev — every Pekulo\* DS component that ships a fill-the-cell list AND will also render flat on mobile)

- **Date:** 2026-05-17
- **Mistake:** Story 1-4's `MilestonesSection` inner `<ul>` was styled with `flex={1} minHeight={0} style={{ overflowY: "auto", ... }}` so it would fill the bento cell's row track on desktop and scroll the milestones list inside the cell when count > 6. This shape depends on a parent with a fixed height (the bento cell, sized by `grid-auto-rows: minmax(220px, auto)`). When story 2-3 added the cap-view mobile flat branch and rendered `<MilestonesSection flat />` inside a natural-flow column (`<View flexDirection="column" gap={40}>`), the `<ul>`'s `flex:1` had no fixed reference height to fill → CSS resolved it to 0 px → the milestone rows were rendered in the DOM but invisible (the section header showed `+ Ajouter` but no rows underneath). The Paliers data quality regression was invisible to typecheck, lint, and snapshot tests — only caught by the user's visual side-by-side at viewport 768 vs the desktop bento at 1440.
- **Correction:** Gate the fill-the-cell styles on the `flat` prop. When `flat={true}`, drop `flex:1 + minHeight:0` and switch `overflowY: "auto"` → `"visible"` so the list flows naturally and lets the page-level column scroll handle overflow. When `flat={false}` (the default — bento mode), keep the original fill-the-cell shape. Same pattern needed for `<View render="ul" flex={...} ...>` in any other DS component (future `CompositionList`, `RecentActivityList`, `HoldingsList`, `TransactionsList`).
- **Rule:** When a Pekulo\* DS component renders a list/grid that's designed to fill a fixed-height parent (bento cell), AND that component might also render in a flat-flow context (mobile single-column stack), the fill styles MUST be conditional on `flat`. Concretely:
  - `flex: {flat ? undefined : 1}`
  - `minHeight: {flat ? undefined : 0}`
  - `overflowY: {flat ? "visible" : "auto"}`
    Verification step at GREEN: screenshot the component at viewport ≤ 1023 (in flat mode) AND at viewport ≥ 1024 (in bento mode); confirm rows are visible in both. A typecheck-only signal is insufficient — visual confirmation via `next-browser` is the only catch.

### 2026-05-17 — Tamagui v5 media keys: `$max-md` / `$gtSm` / `$gtMd` DO NOT EXIST in `@tamagui/config/v5` ; breakpoints are sm:640 md:768 lg:1024 xl:1280 (supersedes the 2026-05-13 claim that "Pekulo Tamagui `md: 1020`") (Scope: aped-dev, aped-arch, aped-review — every Pekulo\* DS component and every apps/web responsive layout)

Bug invisible until story 2-3 forced a tablet screenshot via next-browser.

- **Correction:** Introduced a `decimalToNumber(value, fallback)` helper at the top of `hypothesis.service.ts`: returns the fallback for `null`/`undefined`, passes plain numbers through, and prefers `.toNumber()` on `Prisma.Decimal` instances (explicit, lintable, throws on `Infinity`). Tests now construct fixtures with real `Prisma.Decimal` instances and pin the `Number.MAX_SAFE_INTEGER` boundary to surface a regression instead of accumulating float drift.
- **Rule:** Every Prisma → DTO boundary that touches a `@db.Decimal` column MUST coerce via `.toNumber()` (or a guarded helper), NEVER via `Number(...)`. Tests for these services MUST seed mock returns with real `Prisma.Decimal` instances — JS numbers slip through and hide the production coercion path. The V1 tolerance budget assumes monetary values ≤ `1e7` (Alex personal-use scale); when a feature lands a value that could exceed `Number.MAX_SAFE_INTEGER` (e.g. portfolio totals in cents at scale, projection-curve compounded balances in story 1-2), revisit the coercion strategy — Decimal-as-string at the wire is the next belt loop.

### 2026-05-04 — Bun `--frozen-lockfile` in Docker requires every workspace member's package.json (Scope: aped-arch, aped-story, aped-dev — stories 0-3, 0-8, every apps/\* Dockerfile)

- **Date:** 2026-05-04

  2. **`.dockerignore` exception for foreign workspace manifests** — `apps/web` exclusion stays (we don't want 2 GB of Next.js sources in the apps/api build context), but add `!apps/web/package.json` immediately after to re-include just the manifest.
